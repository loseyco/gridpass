# Firebase Dynamic SSR Hosting & Cloud Run Deployment Analysis

This report details the architectural investigation of the Firebase Dynamic SSR hosting setup, Next.js framework-aware build configurations, and Google Cloud Run deployment pipeline for `gridpass.app` (Gridpass-v4).

---

## 1. Firebase JSON & Deployment CLI Tools

### `firebase.json` Analysis
The `firebase.json` configuration at the root of Gridpass-v4 is structured as follows:

```json
{
  "firestore": {
    "rules": "firestore.rules"
  },
  "storage": {
    "rules": "storage.rules"
  },
  "hosting": {
    "source": ".",
    "ignore": [
      "firebase.json",
      "**/.*",
      "**/node_modules/**"
    ]
  }
}
```

#### Key Architectural Findings:
* **Framework-Aware Integration (`"source": "."`)**: Rather than utilizing the traditional `"public"` directory for static hosting and manual rewrite rules to Cloud Functions, this project leverages the modern **Firebase Framework-Aware CLI** (historically enabled via the `webframeworks` experiment).
* Setting `"source": "."` instructs the Firebase CLI to automatically detect the underlying framework in the root directory (Next.js), coordinate the framework build process locally, and split the resulting outputs into static and serverless targets automatically.

### CLI Tools & Commands Available
The deployment process is entirely driven by the **Firebase CLI (`firebase-tools`)**:
* **Active CLI Binary**: Installed globally on the user system at `C:\Users\pjlos\AppData\Roaming\npm\node_modules\firebase-tools\lib\bin\firebase.js`.
* **Detected Version**: `15.17.0` running under Node `v24.13.0` on `win32` platform (extracted from log).
* **Core Deploy Commands**:
  1. `firebase experiments:enable webframeworks`: Must be executed once on the machine to allow the CLI to parse the `"source": "."` directive and compile the Next.js integration.
  2. `firebase deploy`: Automatically runs the framework detection, performs a full production Next.js build, compiles the serverless wrappers, uploads the static hosting assets, and provisions the Cloud Run (Gen 2 Function) instance.
  3. `firebase deploy --only hosting`: Targets only the hosting stack, which includes both the static CDN assets and the dynamic SSR Cloud Run wrapper since they are logically bound under the Hosting configuration.
  4. `firebase emulators:start`: Starts the local Firebase emulator suite. The framework-aware integration boots a local wrapper server mimicking the Cloud Run SSR execution environment, allowing for full local testing of dynamic routing and SSR.

## 2. Next.js Configurations & Dynamic SSR Packaging

### Configuration & Package Scripts
* **`package.json`**:
  * Next.js Version: `"16.2.6"` (running React `"19.2.4"`).
  * Build script: `"build": "next build"`.
  * During deployment, the Firebase CLI automatically executes the `npm run build` command, building the site under the `Turbopack` compiler.
* **`next.config.ts`**:
  * Currently contains a default, clean export:
    ```typescript
    import type { NextConfig } from "next";
    const nextConfig: NextConfig = {
      /* config options here */
    };
    export default nextConfig;
    ```
  * Note: No custom server or target overrides are specified because the Firebase CLI handles wrapping the output.

### The Under-the-Hood Dynamic SSR Build Process
When `firebase deploy` runs and Next.js successfully compiles, the Firebase CLI compiles and populates a `.firebase` build cache directory (`.firebase/gridpass/`):

```
.firebase/gridpass/
├── hosting/            <-- Pure static assets uploaded to global CDN
└── functions/          <-- Serverless SSR Node.js runtime wrapper for Cloud Run
```

#### A. Static CDN Layer (`.firebase/gridpass/hosting/`)
* Pre-rendered static pages (e.g. `index.html`, `login.html`, `features.html`, `pricing.html`) and all bundle assets (`_next/static/`) are output here.
* These assets are deployed directly to Firebase Hosting's global CDN Edge, ensuring instantaneous response times for static paths without invoking the server.

#### B. Dynamic Serverless / Cloud Run Layer (`.firebase/gridpass/functions/`)
* Any dynamic SSR paths, API endpoints, or middleware functions are bundled into a standalone, isolated server environment.
* **Autogenerated `package.json`**:
  * Target engines are compiled to Node 24: `"engines": { "node": "24" }`.
  * Injects critical serverless dependencies: `"firebase-frameworks"` and `"firebase-functions"`.
  * Copies over Next.js and all production dependencies of the project.
* **Entrypoint `server.js`**:
  * Automatically sets up a **Gen 2 Cloud Function** (which executes natively on **Google Cloud Run** under the hood).
  * The file content is:
    ```javascript
    const { onRequest } = require('firebase-functions/v2/https');
    const server = import('firebase-frameworks');
    exports.ssrgridpass = onRequest({}, (req, res) => server.then(it => it.handle(req, res)));
    ```
* **Routing Rewrites**: Firebase Hosting automatically configures routing rules under the hood so that all traffic not hitting a pre-rendered static CDN asset is proxied directly to the `ssrgridpass` Cloud Run instance.

## 3. Requirements for a Clean Build & Dynamic Deployment

Our investigation of the environment logs reveals specific errors and folder states that must be handled to ensure a successful dynamic deployment.

### A. Critical Code Compilation Fix (Required)
The current build fails during the Next.js compilation step (`next build`) due to a TypeScript type mismatch in **`src/app/dash/page.tsx`**.

#### The Error (from `firebase-debug.log`):
```
[info] ./src/app/dash/page.tsx:290:52
Type error: Object literal may only specify known properties, and 'accuracy' does not exist in type '{ lat: number; lng: number; }'.

  288 |           device: 'Webcam/Simulation',
  289 |           userAgent: 'Mozilla/5.0...',
  290 |           location: { lat: 42.3601, lng: -71.0589, accuracy: 10 }
      |                                                    ^
```

#### Diagnostic Breakdown:
* The `DashboardTagScan` interface (lines 80-92) defines the `location` property as:
  ```typescript
  location?: { lat: number; lng: number } | null;
  ```
* However, in the simulated/mock state (around line 290 in earlier drafts, currently corrected in the main file or caching version mismatches), the object was supplied with an extra `accuracy` property:
  ```typescript
  location: { lat: 42.3601, lng: -71.0589, accuracy: 10 }
  ```
* Under Next.js and TypeScript's `"strict": true` rules, object literal strict type checking fails on undeclared properties.
* **Requirement**: To run a clean build, the target file must have `accuracy` omitted from the location literal or the interface extended. (The current source file `src/app/dash/page.tsx` line 290 shows the property has already been partially updated to `{ lat: 42.3601, lng: -71.0589 }` in some revisions, but any stale files or cached compilations containing `accuracy` will cause the Next.js build worker to crash with exit code `1`).

### B. Directory Sanitation Requirements (Clean Builds)
To avoid caching inconsistencies or `ENOENT: no such file or directory` errors (like the `export-marker.json` error in the logs), execute the following cleanup before deploying:
1. **Remove Next.js cache**: Delete the `.next/` directory.
2. **Remove Firebase deploy cache**: Delete the `.firebase/` directory to force the Framework-aware CLI to rebuild the dynamic serverless environment from scratch.

### C. Environment Requirements
* **Node.js Alignment**: The local compiler node version should ideally be Node.js 24 (`v24.13.0` was detected in the success path) to match the autogenerated Cloud Functions engines configuration.
* **Environment Files**: The build process parses and injects environment variables defined in `.env.production.local` during the compilation of dynamic assets. This file must be fully populated with all live API secrets (Firebase, Stripe, Maps, Gemini) prior to running `firebase deploy`.
* **Experiment Active**: Ensure the workspace CLI has the frameworks experiment active by running `firebase experiments:enable webframeworks`.
